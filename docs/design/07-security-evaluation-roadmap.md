# 安全、评测与实施路线图

## 1. 风险模型

Finding Ledger 的主要风险并不只来自数据库故障，还来自错误知识被长期保存后反复影响 Agent 的判断。设计应覆盖以下风险：

| 风险 | 可能后果 | 缓解措施 |
|---|---|---|
| 无证据的猜测被提升为事实 | 后续推理持续建立在错误前提上 | 默认 unassessed/provisional；supported 必须满足证据校验 |
| scope 过宽 | 把旧版本或另一任务的发现错误复用 | match/context 分开；未知范围不默认匹配 |
| 证据源发生变化 | 引用指向新内容，旧判断失去依据 | 保存 revision/content_hash；变化时提示核验 |
| 反证丢失或被覆盖 | Agent 重走已排除路径 | 反证作为状态和事件保存，不物理删除 |
| 注入内容过多 | 上下文被历史记录占满，降低当前任务质量 | 确定性检索、token 预算、短摘要和按需展开 |
| 恶意或有害文本进入 evidence | 提示注入或不可信指令被重新注入 | 将证据视为数据而非指令；限制摘要与外链加载 |
| 项目之间泄漏 | 某项目的路径、约束或结论出现在另一个项目 | 稳定 project identity；跨项目共享默认关闭 |
| 敏感数据被保存 | token、个人信息或客户数据长期滞留 | 写入前脱敏、限制 excerpt、提供删除/清理流程 |

## 2. 安全和隐私要求

- **本地优先：** 数据库默认保存在用户控制的位置；没有明确需求，不上传日志或完整证据内容。
- **最小留存：** 保存证据定位符和短摘要，原始日志尽量保留在原系统。
- **秘密信息过滤：** 对 API key、凭据、cookie、私密路径和可能的个人/客户数据进行脱敏或拒绝持久化。
- **来源为不可信数据：** finding/evidence 内容可能来自外部网页、日志或用户粘贴文本，不得将其中的指令直接当作系统指令执行。
- **项目隔离：** 查询必须先确定项目身份；跨项目检索应明确启用，不能因关键词相似自动共享。
- **外部副作用需审批：** 修改 AGENTS.md 或其他项目文件之前，需要明确授权与审阅。
- **用户可纠错和清理：** 提供撤回、归档和按项目导出/删除能力；在不物理删除的默认模式之外，隐私清理需求应有明确的受控删除路径。

## 3. 测试策略

### 单元测试
- claim_kind、epistemic_state、lifecycle_state 的枚举与组合；
- evidence relation 与 finding relation 的语义区分；
- scope_json 校验和 unknown/incompatible 判定；
- 状态转换合法性与拒绝路径；
- supersedes 环路、自指和目标不存在；
- statement 更新是否保留事件或要求新 finding；
- project identity 的规范化。

### 存储和事务测试
- 所有外键约束在数据库连接中启用；
- refute_finding 写入 evidence、relation、state 和 event 时全成或全败；
- supersede_finding 创建新 finding 与关闭旧 finding 时全成或全败；
- 重复请求不会产生不受控的重复记录；
- 迁移可在备份副本上运行，失败不会破坏原表；
- schema_migrations 能阻止重复执行非幂等迁移。

### 检索与注入测试
- supported + applicable 的关键 finding 被找回；
- refuted 项被呈现为已排除路径，不会呈现为支持性结论；
- superseded 项默认不作为当前事实正文注入；
- scope 不兼容的记录不进入当前候选；
- scope unknown 的记录带有明确警告或被延后；
- token 预算不足时保留状态、ID 和硬性条件；
- DB 或宿主事件失败时有清晰回退，不阻塞主要任务。

### 回归测试集
建立人工标注的案例集，覆盖：
1. 同一项目、同一版本的重复调试；
2. 代码变更后复用历史结论；
3. 同一结论在两个配置下分别成立/不成立；
4. 旧结论被反证；
5. 新结论取代旧结论；
6. 用户约束与实验事实混合；
7. 两条结论互相冲突但适用范围不同；
8. 引用路径失效或内容哈希变化。

## 4. 评测方案

与无 ledger、全部历史注入以及按相关性检索三个基线比较：

- **重复排查率：** 已记录且适用的探针被重复执行的比例；
- **结论召回率：** 后续任务所需的有效 finding 被找回的比例；
- **误注入率：** scope 不匹配或 superseded 内容作为当前事实注入的比例；
- **错误确信率：** provisional、contested 或缺证据记录被表述为确定事实的比例；
- **证据追溯率：** 注入结论中可以定位到原始来源的比例；
- **token 效率：** 每千 token 带来的重复步骤减少量或任务完成率变化；
- **延迟：** 新会话初始化和 compaction 后检索耗时。

验收不应只看 recall。若记忆提高召回却增加过期知识误用，产品收益可能为负。每个指标需要给定测试集与计算定义，不能凭单次示例宣布改善。

## 5. 实施路线图

### P0：可信数据闭环
- 新 schema、schema_migrations 和旧数据迁移；
- log_finding、query_findings、get_finding、add_evidence；
- set_finding_state、refute_finding、supersede_finding；
- 状态事件和事务一致性；
- 单元/集成测试与迁移审计报告。

完成标准：不能无证据地把主张标为 supported；反证与取代操作全成或全败；历史记录可追溯。

### P1：项目与 scope 可靠性
- 稳定 project identity；
- scope match/context/revalidate_on 解析器；
- 项目隔离、版本提示和 needs_revalidation 行为；
- 来源变化检查与关键证据引用的可访问性检查。

完成标准：明确不适用的 finding 不会以当前事实形式注入；信息未知时不会默认为适用。

### P2：宿主集成与预算化注入
- 验证真实 harness 事件与 prompt assembly 接口；
- 新会话和 compaction 后检索；
- 状态感知的格式化；
- token budget、失败回退和注入可观测性。

完成标准：压缩恢复稳定、注入内容可追溯且有上限，数据库故障不阻塞用户任务。

### P3：评测驱动优化
- 建立标注回归数据集和基线；
- 评估关键词、标签与简单规则的召回；
- 只有当指标证明必要时再加入 embedding/reranker；
- 评估自动候选发现、去重与冲突提示；
- 检验从 finding 提议规则的端到端审批流程。

完成标准：以可重复的指标证明重复排查或错误复用下降，且 token 与延迟成本处于可接受范围。

## 6. 明确不进入 V1 的内容

- 为每条 finding 生成未经校准的 0–1 confidence；
- 自动根据措辞或模型自评提升证据状态；
- 一开始就接入向量数据库或远程存储；
- 自动把所有会话结论写入长期记忆；
- 根据时间年龄单独判定事实过期；
- 无需用户批准就修改 AGENTS.md；
- 将 finding ledger 发展为完整的会话存档或文档平台。

这些能力只有在 V1 的正确性、检索收益和可运维性得到验证后才值得考虑。
